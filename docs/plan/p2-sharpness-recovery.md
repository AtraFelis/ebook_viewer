# P2 — 스크롤 중 선명도 복구 지연 개선

2026-10-17 사용자 결정: 스크롤 중 잠시 흐리다가 선명해지는 현상은 P2에서 개선한다. P1 완료 조건에 추가하지 않는다.

2026-10-18 착수 계획: 이번 개선은 [P2 전체 범위/완료 기준](p2-scope-and-completion.md)의 한 부분이다. API 33 엔진/SDK 확장 경로와 구성 승인을 먼저 확인하고 기준선·선명화 지표·합격선을 고정한다. 일반 스크롤 정지 후 95% 선명화 p95 500ms 이하 또는 기준 대비 30% 개선 등은 측정 전 제안이며 현재 달성 결과가 아니다. 엔진 변화가 있으면 P1과 새 엔진을 구분해 측정하고 다른 P2 기능을 포함한 최종 앱에서도 재확인한다.

## 현상과 확인된 구조

사용자는 연속 스크롤로 새 영역에 진입하면 잠시 흐릿하게 표시된 뒤 해상도가 복구된다고 보고했다. 현재 코드에는 전체 페이지의 긴 변 최대 512px 미리보기를 먼저 그리고, 현재 배율의 가시 512px 타일로 덮어쓰는 경로가 있다. `PdfCanvasView.updateTiles/onDraw`, `PdfWorker.request/schedule`, `DocumentLayout.visibleTiles`가 관련 지점이다.

고해상도 요청은 현재 가시 영역만 대상으로 한다. 스크롤 방향 앞쪽의 화면 밖 타일을 미리 준비하는 구현은 없다. 단일 PDF worker가 한 번의 작업에서 최대 4개 타일을 처리하고 다음 작업을 큐에 넣는다. 새 요청이 오면 세대를 갱신해 이전 작업을 중단/교체하되 여전히 필요한 완료 타일은 사용할 수 있다. 빠른 스크롤의 반복 요청은 선명한 타일이 준비되기 전에 영역이 바뀌는 원인이 될 수 있다. 큰 배율에서는 같은 미리보기를 더 늘려 보므로 흐림이 두드러질 수 있지만, 확대 상한 변경만으로 같은 배율의 처리량이 증가했다고 단정하지 않는다.

이는 코드와 증상이 부합한다는 진단이다. 사용자의 실제 PDF에서 타일 대기·native render·캐시 미스의 시간 기여도는 측정하지 않았다. P0 프레임 결과와 기능 테스트 통과는 선명도 복구 지연이 없다는 검증이 아니다. 앞선 100페이지 메타데이터 조사 시간과 이 지연은 서로 다른 지표다.

## 2026-10-18 추가 관찰 — 낮은 DPI와 체감 지연

사용자는 ‘PDF의 DPI가 낮을수록 선명도 복구가 오래 걸리는 것 같다’고 보고하고 낮은 DPI와 화질의 관계를 물었다. 실제 해당 파일의 이미지 픽셀 수/배치 크기/인코딩이나 지연 시간을 확인하지 않았으므로 **사용자 관찰에 따른 미검증 가설**로 기록한다. 육안 화질 차이를 DPI 측정 결과로 취급하지 않는다.

여기서 구분할 값은 PDF 전체의 단일 DPI가 아니라 포함 이미지의 픽셀 수와 페이지에 배치된 크기에 따른 유효 PPI, 그리고 앱의 화면 렌더 배율이다. 같은 크기로 표시하는 이미지의 실제 해상도가 낮으면 원본의 세부 표현이 제한될 수 있다. 메타데이터의 DPI 숫자만 바꾸는 것과 실제 픽셀 수/내용 변경은 구분한다([Adobe 이미지 크기·해상도](https://helpx.adobe.com/photoshop/desktop/crop-resize-transform/resize-adjust-resolution/image-size-resolution-and-resampling.html)). 벡터 텍스트·도형은 이미지 해상도와 별도로 다룬다([Adobe 벡터/비트맵](https://helpx.adobe.com/ca/photoshop/using/image-essentials.html)).

현재 앱의 요청 크기/타일 수는 `DocumentLayout.visibleTiles`의 페이지 크기·페이지 배치 배율·viewport 줌/화면 크기로 결정하고, `PdfCanvasView.updateTiles`는 긴 변 최대 512px 미리보기를 요청한다. 이 요청 경로는 PDF 이미지 DPI 메타데이터를 읽어 저DPI 문서를 별도 지연시키지 않는다. 이는 native 렌더 내부의 이미지 디코딩/보간·압축 형식 영향이나 사용자 체감 차이가 없다는 뜻은 아니다. 원인별 시간은 아직 미측정이다.

P2 기준 측정 자료에 다음 비교를 추가한다. 현재 샘플 생성/기기 실행은 하지 않았다.

- 같은 원본 패턴·페이지 크기·배치 크기의 스캔 합성 자료를 실제 픽셀 해상도만 달리해 준비한다(예: 75/150/300 PPI). 먼저 같은 인코딩 계열로 비교하고 압축 방식/품질 차이는 별도 조건으로 둔다. 숫자는 시험 조건 후보이며 개인 PDF의 측정값이 아니다.
- 동일 픽셀/배치 크기에서 이미지 DPI 메타데이터만 바꾼 대조군과 벡터 대조군을 둔다. 다른 배율/페이지 크기·압축·문서 복잡도를 해상도 단독 원인으로 오인하지 않는다.
- 같은 viewport·스크롤·캐시 조건에서 worker 대기, native render, 실제 가시 타일 draw 시각과 최종 원본 화질을 나눠 비교한다. 원본이 흐린 채로 렌더 완료된 상태를 타일 미준비나 영구 복구 지연으로 세지 않는다.

## 2026-10-18 분석 화면 추가 — 픽셀 수·용량·색상 형식 구분

사용자가 제공한 분석 화면에서 두 번째 페이지가 더 오래 걸렸다고 확인했다. 원본 PDF/페이지 내용은 받거나 복제하지 않았으며 다음은 화면에 표시된 이미지 속성만의 비교다. 분석 도구의 값/단위/추출 방식과 앱의 실제 실행 시간은 독립 검증하지 않았다.

- 첫 이미지: 1446×2237px(약 323만 픽셀), 표시 용량 149.2KB, DeviceGray/8bpc/DCTDecode, 표시 DPI 300.
- 두 번째 이미지: 1407×2223px(약 313만 픽셀), 표시 용량 284.6KB, DeviceRGB/8bpc/DCTDecode, 표시 DPI 600.
- 두 번째의 픽셀 수는 약 3.3% 적고 용량은 약 1.9배다. 이 자료는 ‘저DPI 또는 픽셀 수가 클수록 느리다’를 뒷받침하지 않는다. 저장 데이터 용량/그레이·RGB/압축 내용/배치 크기 차이를 함께 확인해야 한다. 양쪽 필터 이름이 같아도 디코딩 비용이 같거나 용량에 정비례한다고 결론내리지 않는다.
- 분석 화면의 DISPLAY SIZE도 서로 다르다. 단위는 미확인이어서 PDF point/화면 px로 단정하지 않고 실제 페이지/이미지 변환 행렬과 함께 확인한다. 비교 시 같은 화면상 페이지 너비로 맞춘 결과와 원시 줌·타일 렌더 배율·요청 수를 같이 남긴다.

수정한 가설은 **비슷한 이미지 픽셀 수에서 이미지 디코딩/색 변환 등의 native 처리 차이가 지연에 기여할 수 있다**는 것이다. 첫/두 번째 페이지의 방문 순서, 미리보기·타일 캐시, 큐 대기 차이도 남아 있어 특정 원인을 확정하지 않는다. 페이지 전체가 더 느린 것인지, 화면에서 미리보기가 타일로 교체되는 대기가 긴 것인지도 계측으로 구분한다.

추가 비교는 동일 패턴·픽셀 수·페이지/배치 크기의 그레이/RGB 합성 문서 및 같은 색상에서 압축 품질/내용을 나눈 대조군으로 한다. A→B/B→A 방문, cold/warm 캐시를 바꿔 미리보기·첫 타일·반복 타일 render 시간/횟수와 큐 대기를 기록한다. 이미지를 타일마다 다시 디코딩하는지는 미확인이다. native trace/계측 근거 없이 재디코딩을 확정 원인으로 쓰지 않는다.

현재 앱의 출력 타일은 원본 색상과 관계없이 `Bitmap.Config.ARGB_8888`이다. 원본 RGB가 그레이보다 출력 타일 캐시 메모리를 3배 쓴다고 해석하지 않는다. [공식 render 계약](https://developer.android.com/reference/android/graphics/pdf/PdfRenderer.Page#render(android.graphics.Bitmap,%20android.graphics.Rect,%20android.graphics.Matrix,%20int))도 목적 비트맵의 ARGB를 명시한다. native 디코더의 내부 작업 메모리는 별도 계측 대상이다.

## P2 개선 순서

1. 같은 기기/문서/배율/스크롤 속도에서 새 영역 진입→첫 선명 타일→가시 영역 선명화 시간의 분포를 측정한다. worker 대기와 render 시간, 요청 교체 횟수, 캐시 적중을 구분한다. 원문·URI·페이지 이미지/추출 텍스트를 로그나 외부로 보내지 않는다.
2. 가시 영역을 항상 우선하면서 스크롤 방향 앞쪽의 제한된 타일을 준비한다. 방향 반전/문서 전환 시 불필요한 작업을 취소하고 동일 타일 요청의 재사용/중복 렌더를 검토한다.
3. 결과에 따라 미리보기 해상도/단계별 캐시를 조정한다. 미리보기 증대만으로 해결됐다고 판단하지 않고 선명 타일 준비 시간과 메모리 영향을 함께 비교한다.

## 검증과 제약

- 변경 전후 같은 조건에서 첫 방문/캐시 재방문, 저속 스크롤/빠른 플링/반전, 높은 배율, 벡터·스캔 자료를 비교한다. 목표 수치는 기준 측정 후 정하며 측정 없이 무지연을 보장하지 않는다.
- 선명화 지연뿐 아니라 프레임/ANR/OOM, 64MiB 공유 캐시, 취소/자원 수명과 줌/앵커 유지도 회귀 검증한다.
- UI 스레드 PDF 렌더/I/O, 전체 고해상도 페이지 선로딩, 영구 저해상도로의 대체를 도입하지 않는다. 새 런타임 의존성은 AGENTS의 별도 승인 규칙을 따른다.
- 이번 P1 배경색 구현은 이 개선을 수행하거나 통과한 것으로 보고하지 않는다.
